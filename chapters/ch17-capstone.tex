\chapter{The Capstone: Decisions and Trade-offs}
\label{ch:capstone}

\begin{quote}\itshape
The code is the easy half. The section explaining why it is shaped this way is

\noindent
Ops Copilot is finished by the time you reach this chapter; it was built a stage
at a time across the preceding sixteen. This chapter deliberately introduces no
new API. It walks the completed system as a set of decisions --- what was chosen,
what was rejected, and what it cost.

% ============================================================
\section{The system}
\label{sec:capstone-system}
\index{Ops Copilot}
\index{capstone}

\mermaidfig{capstone-architecture}{%
  The finished system. Every arrow is a chapter.}{%
  Ops Copilot, assembled.}

A FastAPI service holding an agent built once in \code{lifespan}. A request
acquires a per-thread advisory lock, then runs a \api{StateGraph} whose middleware
audits, redacts and limits. The graph retrieves, fans out over the retrieved
documents with \api{Send}, synthesises, and --- for the one irreversible action ---
stops at an \api{interrupt} until a human answers. State lives in Postgres, so
any pod can serve any conversation and a paused run is a row rather than a held
thread.

\section{The decision log}
\label{sec:decisions}
\index{decision log}

Each entry: the choice, the rejected alternative, the reason, the cost.

\subsection{Single agent rather than a supervisor}

\textbf{Rejected:} a supervisor routing to specialist workers.
\textbf{Reason:} Chapter~\ref{ch:multi-agent} measured the structural overhead at
2.8$\times$ the context and 2.5$\times$ the model calls, with three of five calls
spent on routing rather than work. None of the four symptoms that justify
multi-agent applied --- the prompt is manageable, there are five tools, the
parallelism we need is \api{Send} within one agent, and nothing needs an
independent critic.
\textbf{Cost:} if the tool count grows past twenty
(Chapter~\ref{ch:tools}), this decision has to be revisited.
\textbf{What would change it:} the quality half of the experiment, still unrun,
showing a supervisor answers materially better.

\subsection{Postgres rather than Redis}

\textbf{Reason:} durability over latency. Checkpoint writes are not on the
critical path in a workload dominated by provider latency
(Chapter~\ref{ch:asyncio}), and Postgres gives us the advisory lock
(Chapter~\ref{ch:serving}) in the same system.
\textbf{Cost:} higher write latency per superstep than Redis would give.

\subsection{\texorpdfstring{\code{durability="sync"}}{durability sync} on the email path only}

\textbf{Reason:} Chapter~\ref{ch:persistence} showed the mode is per invocation.
The path that can send email pays for the safest setting; question-answering does
not.
\textbf{Cost:} an extra checkpoint write per superstep on one path.

\subsection{An idempotency key rather than a distributed transaction}

\textbf{Reason:} Chapter~\ref{ch:persistence} measured the replay sending the
email twice. A distributed transaction across our database and a third-party mail
API is not available; a key derived from the intent is, and it is what the mail
provider itself supports.
\textbf{Cost:} correctness now depends on the key being derived from the intent
rather than the attempt --- a subtlety that needs a comment and a test.

\subsection{SSE rather than WebSockets}

\textbf{Reason:} the interaction is request-then-stream. SSE traverses proxies
without an upgrade and the browser reconnects for us
(Chapter~\ref{ch:serving}).
\textbf{Cost:} the user cannot interrupt mid-generation; the double-texting
policy is reject-with-409 rather than interrupt.

\subsection{Retrieval as a tool rather than a fixed step}

\textbf{Reason:} not every question needs retrieval, and a fixed step pays for it
every time --- which Chapter~\ref{ch:context} showed is the dominant cost.
\textbf{Cost:} the model sometimes fails to retrieve when it should, which is a
trajectory-evaluation problem (Chapter~\ref{ch:observability}) rather than a
code one.

\subsection{Projecting tool results}

\textbf{Reason:} Chapter~\ref{ch:context} measured 84\% of the bill.
\textbf{Cost:} a projection that drops a field the agent needed is a correctness
regression wearing a cost improvement's clothes --- which is why the stage
contract requires the answers to be unchanged as well as the tokens reduced.

\section{What broke while building it}
\label{sec:what-broke}
\index{troubleshooting!capstone}

Worth recording, because the finished thing conceals it.

\textbf{A load test that measured itself.} Two attempts at
Chapter~\ref{ch:serving}'s benchmark produced nonsense --- first because the
driver shared an event loop with the server, then because the client saturated
before the server did. The tell was the blocking scenario out-throughputting the
clean one. The fix was calibration against a no-op endpoint.

\textbf{No in-box fake implements \code{bind\_tools}.} Discovered while writing
Chapter~\ref{ch:interrupts}'s streaming examples, and it blocks every later
stage's tests until a five-line subclass exists.

\textbf{A visualisation that lied.} A \api{Command}-returning node without a
return annotation draws a graph missing the edge it actually takes
(Ch.~\ref{ch:stategraph}). It runs correctly, so nothing fails --- you simply
believe a wrong diagram.

\textbf{Three documented signatures that were wrong.} The call-limit parameter,
the summarisation trigger and \api{create\_react\_agent}'s status. In every case
the installed package was right.

\section{Writing the decisions document}
\label{sec:writing-decisions}
\index{decision log!writing}

If you build this as a portfolio piece, the decisions document is the
deliverable. A reviewer reads it; nobody reads the code.

\begin{center}
\small
\begin{tabularx}{\linewidth}{@{}XX@{}}
\toprule
\textbf{A worthless entry} & \textbf{A useful one} \\
\midrule
``We used Postgres for persistence.'' & ``Postgres over Redis: durability over
  latency, and it gives us the advisory lock in the same system. Costs write
  latency per superstep.'' \\[3pt]
``We added a human approval step.'' & ``The gate is its own node because code
  before \code{interrupt} re-runs on resume --- measured at twice.'' \\[3pt]
``We used a single agent.'' & ``Measured a supervisor at 2.8$\times$ context for
  no measured quality gain. Revisit past twenty tools.'' \\
\bottomrule
\end{tabularx}
\end{center}

The difference is the rejected alternative and the cost. An entry without both is
a description of what exists, and what exists is already visible in the
repository.

\begin{note}
The same applies in an interview. ``I used LangGraph'' invites no follow-up. ``I
used a single agent because I measured the supervisor at nearly three times the
context for no quality gain I could demonstrate, and I'd revisit it if the tool
count grew'' is a conversation --- and it is the same sentence you would write in
the document.
\end{note}

\section{What is deliberately missing}
\label{sec:missing}
\index{scope!deliberate omissions}

\begin{itemize}[leftmargin=1.4em]
\item \textbf{Multi-tenancy beyond namespacing.} Store namespaces isolate
      (Ch.~\ref{ch:persistence}); a real multi-tenant deployment needs
      row-level security and a tenancy story for the checkpointer.
\item \textbf{Retrieval quality.} Retrieval is a tool that works; chunking,
      hybrid search and reranking are a book of their own.
\item \textbf{A queue for long work.} Chapter~\ref{ch:serving} argues for it and
      the mini-project stays synchronous, because the tasks are short enough.
\item \textbf{Fine-tuning, and self-hosted models.} Out of scope throughout.
\end{itemize}

\section{Where to go next}
\label{sec:ch17-next}
\index{further reading}

Three things, in the order that pays.

\textbf{Run the three outstanding experiments.} They are specified, the harnesses
exist, and each converts a labelled judgement into a fact.

\textbf{Put the evaluation set in front of an upgrade.} Chapter~\ref{ch:security}
argued the pin-and-upgrade posture; the evaluation set is what makes it safe, and
it is the practice most teams skip.

\textbf{Read the package.} Every chapter of this book found something where the
installed code and the published description disagreed. That will keep being true
after this book is stale --- and it is the habit, rather than any particular fact
in here, that is worth taking away.

\begin{projectbox}
\textbf{Final stage.} The assembled service plus \code{docs/DECISIONS.md}.

Nothing new is built. The deliverable is the document, and its contract is
explicit: each entry states the choice, the rejected alternative, the reason and
the cost. Entries that only record what was built do not count --- the rejected
options are the content.
\end{projectbox}
